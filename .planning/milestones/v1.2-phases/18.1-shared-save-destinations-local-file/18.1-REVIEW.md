## Warnings

### WR-01: DictationHUDBinding introduces a structural retain cycle that the comment claims is broken

**File:** `PSTranscribe/Sources/PSTranscribe/App/DictationCoordinator.swift:112-119, 526-527`

**Issue:** The comment above `attach()` (lines 112-116) states: "The closure is captured weakly to break the coordinator <-> windowController retain pair." After the gap-08 rewrite, `DictationHUDBinding` holds `coordinator` as a strong `let` field (line 527). `attach()` passes `self` (the coordinator) into `DictationHUDBinding(coordinator: self)`, which is then wrapped in an `AnyView` and stored by the window controller. The `windowController` property is a strong `var` (line 122). The resulting object graph is:

```
DictationCoordinator
  -> windowController: DictationWindowController?   (strong var)
     -> content: AnyView
        -> DictationHUDBinding.coordinator           (strong let)
           -> DictationCoordinator                   <- cycle closes
```

The `[weak coordinator]` capture inside the `onStop` closure (line 533) breaks only the closure's back-reference; it has no effect on the struct field. The retain cycle is real.

In practice this is not a memory leak -- both objects are app-scope singletons that live for the full application lifetime. However, the comment creates a guarantee that does not hold, and any future code that constructs multiple coordinator/window-controller pairs (e.g., a second dictation mode, tests that construct and release coordinators) would leak indefinitely.

**Fix (minimal -- correct the comment):**

```swift
/// Wave 4 wiring point. PSTranscribeApp (Plan 18-08) constructs the
/// DictationWindowController, then calls `attach(windowController:)` so the
/// coordinator can install DictationHUDBinding as the window's content.
/// DictationHUDBinding holds coordinator strongly; both are app-scope singletons
/// so the cycle is intentional and harmless. If that changes, make windowController
/// weak (and retain DictationWindowController separately at app scope).
func attach(windowController: DictationWindowController) {
```

**Fix (structural -- break the cycle):**

```swift
// Option: declare windowController weak so DictationWindowController is retained
// only by the app scope, not by the coordinator.
weak var windowController: DictationWindowController?
```

Either fix is acceptable for this phase. The comment fix is lower risk.

### IN-02: Mirror-based test introspection in DictationHUDLiveBindingTests will fail silently if DictationHUD property names change

**File:** `PSTranscribe/Tests/PSTranscribeTests/Phase18.1/DictationHUDLiveBindingTests.swift:30-45`

**Issue:** `snapshotHUD` uses `Mirror(reflecting:)` and matches child labels by string -- `"state"`, `"elapsed"`, `"partialText"`. If `DictationHUD` renames any of those stored properties, the guard at line 44 fires, `Issue.record` is called (which marks the test as failed), and the function returns. This is acceptable behavior -- the test does fail when introspection breaks. However, the failure message ("Could not introspect initial DictationHUD body") does not tell a future engineer which property name changed, making diagnosis unnecessarily slow.

This is a known trade-off of Mirror-based introspection and does not require an immediate fix. A minor improvement:

```swift
guard let s = state, let e = elapsed, let p = partial else {
    Issue.record("""
        snapshotHUD: Mirror matched \(mirror.children.map { $0.label ?? "?" }.joined(separator: ", ")).
        Expected labels: state, elapsed, partialText.
        DictationHUD property names may have changed.
        """)
    return nil
}
```
