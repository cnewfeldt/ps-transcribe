## Fixed This Iteration

### IN-01: Tighten clipboard-ordering comment to specify *network* awaits

**Files modified:** `PSTranscribe/Sources/PSTranscribe/App/DictationCoordinator.swift`
**Commit:** `6bee981`
**Applied fix:** Updated the comment at the clipboard-write site (line 244-250) to clarify that the ordering invariant is "clipboard MUST be written BEFORE any *network* await (saveDestinations.save -> Notion API call)", and called out that the dictationLogger flush above is local-disk I/O. Added a note that if a future failure mode makes the local flush block on a slow disk, the clipboard write should be moved above the dictationLogger block.

**Reasoning for the smaller mechanical fix:** The reviewer offered two paths: (a) tighten the comment, or (b) reorder the clipboard write to precede the dictationLogger flush. Per the iteration-2 directive ("prefer the smaller mechanical fix"), I chose (a). The reorder would be the architecturally stronger choice but it changes execution ordering between two distinct subsystems (file flush + clipboard) and would require updating `DictationCommitFlowTests.localFileBodyContainsTranscript` and related tests that may rely on the current ordering. The comment fix preserves all existing semantics and accurately documents the actual ordering invariant.

### IN-02: Document fire-and-forget release race in `PasteboardTestLock`

**Files modified:** `PSTranscribe/Tests/PSTranscribeTests/Phase18/PasteboardTestLock.swift`
**Commit:** `26a6e40`
**Applied fix:** Added a "KNOWN LIMITATION" doc-comment block to `PasteboardTestLock` documenting the `defer { Task { await release() } }` race, why the practical risk is low (`.serialized` already gates intra-suite parallelism; the lock itself gates inter-suite races), and what the future fix path is (convert to an `NSLock`-backed class with synchronous `release()` so each `defer` becomes an explicit `await release()` at end-of-body).

**Reasoning for the doc-only fix:** The reviewer's suggested fix requires either (a) restructuring 6 test files (16 occurrences, several with `guard else { return }` early exits that complicate moving the release out of `defer`), or (b) rewriting the lock primitive (changing actor to a class with NSLock + nonisolated synchronous release). Both are non-mechanical and risk introducing new races during the migration. The reviewer explicitly classified this as "small flakiness risk in CI under load -- not a logic bug" with "low practical risk". Documenting the limitation honestly preserves operational truth and provides the migration recipe for when (if) flakiness is observed. No flakiness has been seen in CI to date.

### IN-03: Document meeting fan-out coupling on Local File path

**Files modified:** `PSTranscribe/Sources/PSTranscribe/Views/ContentView.swift`
**Commit:** `de0fafb`
**Applied fix:** Added a "KNOWN LIMITATION" comment block above the `if !capturedPath.isEmpty, let entry = ...` gate (line 1012) documenting why meetings differ from dictation: meeting markdown is read from the streamed Local File on disk, so there is no in-memory transcript for the fan-out to fall back on. Notes the specific user-facing edge case ("Local File off, Obsidian on" passes the D-20 zero-destination check but produces a library entry with empty `filePath` and no fallback URL) and points at the architectural gap pending a future refactor.

**Reasoning for the comment-only fix:** The reviewer's suggested code change (`primaryFilePath = !capturedPath.isEmpty ? capturedPath : (saveResult.obsidianFileURL?.path ?? "")`) cannot be applied directly because `saveResult` does not exist at the line where `entry.filePath` is set -- the entry update is gated on `capturedPath` BEFORE `saveDestinations.save` is called. Applying the reviewer's literal fix would require restructuring the entire post-session block to call `saveDestinations.save` first, then update the entry -- a non-trivial refactor with risk to the well-tested D-18 fan-out flow. The reviewer offered "or add a comment explaining why meetings differ" as the smaller alternative; that is what was applied. The known gap is now visible to anyone reading the code, with a clear path for the future decoupling refactor.
