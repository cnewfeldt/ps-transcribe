```swift
    /// Apply the user's appearance preference to the panel (Phase 21, D-07).
    ///
    /// `NSAppearance` is the AppKit-native equivalent of SwiftUI's
    /// `.preferredColorScheme` for AppKit-owned panels: assigning
    /// `panel.appearance` flips both the chrome and the `NSVisualEffectView`'s

    func applyAppearance(_ preference: AppearancePreference) {
        guard let panel = window else { return }
        switch preference {
        case .system: panel.appearance = nil
        case .light:  panel.appearance = NSAppearance(named: .aqua)
        case .dark:   panel.appearance = NSAppearance(named: .darkAqua)
        }
    }
```

```swift
/// Phase 21 D-07: re-arming `withObservationTracking` loop that mirrors
/// `AppSettings.appearancePreference` onto the Dictation HUD's NSPanel via
/// `NSAppearance`. The `@Observable` macro emits a registration whenever the
/// tracked block reads `settings.appearancePreference`; the `onChange` closure
/// fires once per mutation; we re-call ourselves to re-register and capture the
/// next change. Loop is bounded by the lifetime of the controller + settings,
/// both of which are app-scoped (live for the whole process).
@MainActor
private func observeAppearance(
    controller: DictationWindowController,
    settings: AppSettings
) {
    withObservationTracking {
        // Read the property to register the dependency. We don't apply it here;
        // the synchronous initial application is the caller's responsibility, and
        // `onChange` handles every subsequent mutation.
        _ = settings.appearancePreference
    } onChange: {
        // `onChange` is non-isolated; hop back to MainActor before mutating
        // AppKit windows or recursing.
        Task { @MainActor in
            controller.applyAppearance(settings.appearancePreference)
            observeAppearance(controller: controller, settings: settings)
        }
    }
}
```

This shape mirrors the `applyScreenShareVisibility` pattern (where AppSettings drives an AppKit window property mutation) but uses `withObservationTracking` rather than `.onAppear` because the HUD panel exists for the whole app lifetime; we want every mutation to propagate live, not just the initial one. The recursive re-registration is the canonical `@Observable` continuation pattern under Swift 6.2 — `withObservationTracking` registers exactly one fire, so the closure must re-call itself to keep observing.

**Why not `Task { for-await ... }` or AsyncStream?** `@Observable` doesn't expose an AsyncSequence; it's `withObservationTracking`-driven by design. The recursive shape is the documented pattern (Apple's WWDC 2024 "Observation in Swift" session, slide deck on multi-mutation tracking).

**Why not @MainActor.assumeIsolated inside `onChange`?** Swift 6.2 strict concurrency rejects `assumeIsolated` here because the `onChange` closure has no inherited isolation guarantee. `Task { @MainActor in ... }` is the conservative path that compiles cleanly and adds no measurable latency for a UI-driven event that happens at most once per user click.

**Verify Sendability:** Both `DictationWindowController` and `AppSettings` are `@MainActor`-isolated. The `Task { @MainActor in ... }` capture lifts both references safely. No `Sendable` warnings expected; if any appear, the underlying classes need a `@MainActor`-aware capture list — but none should because the surrounding `init()` is already `@MainActor` (the whole `App` body is).

**Do NOT** add this observation in any other location. The single wire-up is in `PSTranscribeApp.init()` (the natural app-scope home), and the helper is module-private (`fileprivate` would be acceptable too; `private` at module scope means file-scope in Swift, which is what we want).

**Do NOT** introduce KVO, NotificationCenter, or Combine. `withObservationTracking` is the path locked by D-07's "mirrors the existing `applyScreenShareVisibility` pattern" guidance and the project's @Observable convention.
