## Resolution

root_cause: |
  TWO defects, both in the chooseFolder UX, neither involving a missing SF Symbol:

  (a) "Icon not rendering" symptom is a MISDIAGNOSIS in the bug report. The Obsidian Choose-Folder button has no icon in the code. It is `Button(settings.obsidianFolderPath.isEmpty ? "Choose..." : "Change...")` — a plain text label. There is no Image/Label/SF Symbol in any button in SettingsView. The most likely real cause of what the user saw:
    - They were referring to the gray vault-detection status Circle (line 144-146) at the top of the Obsidian section — which renders gray when no folder is configured. To a user expecting an actionable "icon" near the Choose button, a gray circle "not lighting up" can read as "icon not rendering."
    - Or they are misattributing the macOS default folder-glyph that NSOpenPanel itself renders (in its file-browser column) and conflating it with the trigger button.
    - Or — least likely — the SwiftUI Button is being clipped by an enclosing Form/Section layout in a way that hides part of its label on the user's display. (No evidence of this in code.)
   The actionable interpretation: the button label is plain text and renders correctly in code. If a UX uplift to "make the Choose button look like a picker with a folder icon" is desired, that is a feature add, not a bug fix.

  (b) Low-contrast NSOpenPanel title text IS a real defect. Root cause is in
      PSTranscribe/Sources/PSTranscribe/Views/SettingsView.swift lines 645-657. The chooseFolder helper sets only `panel.message` and leaves `panel.title` and `panel.prompt` at their system defaults. On macOS Sonoma+, an NSOpenPanel presented from a SwiftUI Settings window inherits a vibrant/material chrome where the default title bar renders against a translucent background using a label color that has poor contrast in the user's appearance mode. The caller-supplied descriptive string ("Choose the Obsidian folder for transcripts") is bound to `panel.message`, which is a SECONDARY accessory text slot below the title bar — not the title itself. The user perceives the default-styled title text as "the dialog title" and reports it as low-contrast.

fix: |
  Single change in PSTranscribe/Sources/PSTranscribe/Views/SettingsView.swift, lines 647-657. Promote the message string to BOTH the panel title and the action-button prompt, and keep it as the message too so it appears in all three slots (title bar, action button, and accessory message). This guarantees the descriptive string is rendered in the high-contrast title bar slot regardless of the panel's inherited material:

  ```swift
  private func chooseFolder(message: String, onSelect: @escaping (String) -> Void) {
      let panel = NSOpenPanel()
      panel.canChooseFiles = false
      panel.canChooseDirectories = true
      panel.allowsMultipleSelection = false
      panel.title = message              // NEW — high-contrast title bar
      panel.prompt = "Choose"            // NEW — overrides default "Open" action button
      panel.message = message            // unchanged — accessory description

      if panel.runModal() == .OK, let url = panel.url {
          onSelect(url.path)
      }
  }
  ```

  Notes:
  - Setting `panel.title` is the load-bearing change. It puts the descriptive string in the panel's title bar, which is the slot the user is reading.
  - Setting `panel.prompt = "Choose"` is a UX nicety: the default action button reads "Open", which is awkward for a "choose folder" flow. Replacing it with "Choose" matches the in-app button verb. This is optional but consistent with the truth statement ("opens an NSOpenPanel whose title/prompt text is legible").
  - Keeping `panel.message` as well preserves the descriptive accessory text for users who DO read that slot.
  - This single fix repairs the Local File section's picker too (same helper). No caller changes are needed.

  Re: symptom (a) "icon not rendering": there is no code change that would fix a non-existent icon. Recommendation: ask the user to clarify what they mean by "icon" (gray status dot? folder glyph elsewhere? clipped button? expectation that the button SHOULD have an icon as a feature?). If the desired behavior is "Choose-Folder button has a leading SF Symbol (e.g., `folder` or `folder.badge.plus`)", that is a feature-add and should be tracked as a separate UI uplift, not as a 18.1-03 regression fix. A minimal feature add would change line 178-183 to:

  ```swift
  Button {
      chooseFolder(message: "Choose the Obsidian folder for transcripts") { path in
          settings.obsidianFolderPath = path
      }
  } label: {
      Label(settings.obsidianFolderPath.isEmpty ? "Choose..." : "Change...",
            systemImage: "folder")
  }
  ```

  Apply the same to the Local File button at lines 113-118 for consistency.
