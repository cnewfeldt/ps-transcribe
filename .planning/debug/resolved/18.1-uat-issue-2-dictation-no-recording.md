## Current Focus

hypothesis: The DictationHUD is constructed once with **snapshot** values and never re-renders during the live session. When the user presses the hotkey, the engine and state machine actually start, but the visible HUD is frozen at `.idle` (gray dot, "0:00", empty text, no Stop button), so the user observes "nothing appears to be recording."
test: Read DictationCoordinator.attach() + DictationWindowController.setContent() + DictationHUD struct to confirm one-shot snapshot pattern. Confirm there's no reactive re-render path. Verify no test exercises the live HUD.
expecting: Static let-properties on a SwiftUI View hosted via NSHostingView that is never reassigned a fresh rootView during the session.
next_action: Report findings.

expected: Pressing the hotkey starts dictation: HUD shows red pulsing dot, elapsed timer ticks, partial transcript appears as user speaks. ## Evidence

  checked: how the SwiftUI HUD body is wired to live state
  found: `windowController.setContent(AnyView(DictationHUD(state: state, elapsed: elapsed, partialText: dictationStore.volatileYouText, onStop: ...)))` — the `state`, `elapsed`, and `partialText` arguments are evaluated **once** at the time `setContent` is called.   implication: The DictationHUD struct is initialized with `.idle, 0, ""` (the values held by the coordinator at app launch, before any hotkey press). It receives plain `let` properties. No live SwiftUI tracking of `coordinator.state` exists in the HUD's body.

- timestamp: read DictationWindowController.setContent (lines 95-102) and grep for callers

  found: `grep -rn "setContent" Sources/` returns only the single call in `DictationCoordinator.attach()`.   implication: Once attach() runs at app init, the HUD body is permanently frozen at `state=.idle`. Subsequent state mutations (`state = .listening`, `elapsed = N`, `partialText = "..."`) inside `beginDictation` mutate the coordinator's stored properties but do not propagate to the HUD view.

  implication: The HUD-snapshot freeze pre-dates 18.1 (introduced in 18-05/18-06). 18.1 did not cause it; it was simply never exercised end-to-end before.

- timestamp: read TranscriptionEngine.start (lines 145-284)
  checked: Whether the audio path actually fails when called
  found: `start()` performs `ensureMicrophonePermission()`, then `MicCapture.bufferStream(deviceID:)`, then `SystemAudioCapture.bufferStream(...)`.   implication: The engine itself is not the bug. If the engine WERE silently failing (e.g., screen-recording permission missing for system audio), the mic stream would still produce buffers, partial text would land in `dictationStore.volatileYouText`, and `state` would still transition to `.listening`. The user would still see "nothing" because the HUD never reflects those mutations.

## Resolution

root_cause: |
  **DictationHUD is frozen at `state == .idle` for the entire app lifetime.**
  
  `DictationCoordinator.attach(windowController:)` (Sources/PSTranscribe/App/DictationCoordinator.swift:117-129) is called exactly once at app launch from `PSTranscribeApp.init()` (Sources/PSTranscribe/App/PSTranscribeApp.swift:45). It calls `windowController.setContent(AnyView(DictationHUD(state: state, elapsed: elapsed, partialText: dictationStore.volatileYouText, onStop: ...)))`, which **evaluates `state`, `elapsed`, and `partialText` once** and passes them as plain `let` properties on the `DictationHUD` struct.
  
  `DictationWindowController.setContent` (Sources/PSTranscribe/App/DictationWindowController.swift:95-102) reassigns `NSHostingView<AnyView>.rootView` exactly once per call. `setContent` has only one caller in the entire codebase. `windowController?.show()` inside `beginDictation` only calls `orderFrontRegardless()` and does not re-render the SwiftUI subtree. There is no @Bindable, no @ObservedObject, no @Environment, and no Observation read inside the HUD `body` that would cause SwiftUI to subscribe to `coordinator.state` mutations.
  
  Consequently, when the user presses the hotkey:
    1. `beginDictation()` runs to completion
    2. The audio engine actually starts (mic + ScreenCaptureKit)
    3. `state` transitions `.idle -> .loadingModel -> .listening` and `elapsed` ticks
    4. `dictationStore.volatileYouText` populates with partial transcripts
    5. **None of that reaches the HUD** — the panel orders front showing the snapshot taken at app launch: gray dot, "0:00", empty text, **and no Stop button** (because `.idle` hides it).
  
  The user looks at the HUD, sees nothing changing, concludes "nothing is recording," and never presses the hotkey again to commit. Because `endDictation()` is never invoked, no clipboard write occurs and no library entry is created — exactly the symptom reported.
  
  **Why the audio engine probably IS running invisibly:** the menu-bar mic icon (`PSTranscribeApp.swift:186-188`) reads `dictationCoordinator.isActive` via the live @Observable property and DOES update — so the mic icon should pulse. Worth confirming during fix verification: if it pulses, the engine is live; if it does not, the hotkey isn't firing at all (a separate, second bug).

fix: |
  Replace the snapshot pattern with a small live-tracking SwiftUI view that observes the coordinator. A minimal fix:
  
  ```swift
  // New private wrapper view that observes the coordinator.
  private struct DictationHUDBinding: View {
      let coordinator: DictationCoordinator   // @Observable @MainActor final class
      var body: some View {
          DictationHUD(
              state: coordinator.state,
              elapsed: coordinator.elapsed,
              partialText: coordinator.dictationStore.volatileYouText,
              onStop: { Task { @MainActor in await coordinator.endDictation() } }
          )
      }
  }
  ```
  
  Then in `DictationCoordinator.attach`:
  
  ```swift
  func attach(windowController: DictationWindowController) {
      self.windowController = windowController
      windowController.setContent(AnyView(DictationHUDBinding(coordinator: self)))
  }
  ```
  
  Inside `DictationHUDBinding.body`, the reads of `coordinator.state`, `coordinator.elapsed`, and `coordinator.dictationStore.volatileYouText` happen inside SwiftUI's body evaluation — Observation will subscribe to those reads and re-render on mutation. (`TranscriptStore` must also be @Observable; if it isn't, swap `volatileYouText` for an @Observable wrapper or a separately-bound source.)
  
  Add a regression test that mounts the coordinator's HUD against a fake `DictationWindowController` (or test-only host), drives `coordinator._test_setState(.listening)` and `_test_setElapsed(...)`, then asserts the rendered output reflects the new values. Without this test the same regression will recur on the next refactor.
