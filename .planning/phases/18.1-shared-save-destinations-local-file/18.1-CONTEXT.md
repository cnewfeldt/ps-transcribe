# Phase 18.1: Shared Save Destinations + Local File - Context

**Gathered:** 2026-04-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Refactor save destinations into a top-level shared layer in Settings. Three destinations -- **Notion**, **Obsidian**, **Local File** -- each independently configurable. All content producers (meeting recording, voice memo recording, dictation) emit `(content, sessionType)` and a shared `SaveDestinations` layer fans out to whichever destinations are currently enabled.

This unblocks Phase 18 UAT, which was paused after architectural feedback that the dictation-private folder picker (Section("Dictation") with `DictationOutputMode` + `dictationFolderPath`) duplicates what shared destinations should own. Per the architectural rule: **there is no "dictation save"** -- dictation is content like a meeting or voice memo, and it persists to whatever destinations the user has configured.

**In scope:**
- Add `Section("Local File")` as a top-level destination peer to Notion / Obsidian
- Restructure `Section("Obsidian")` to a single folder + frontmatter-based content-type tagging (collapsing today's two-folder shape)
- Add a `session-type` property on Notion entries
- Retire `DictationOutputMode` + `dictationFolderPath`; remove the folder picker from `Section("Dictation")`
- Reduce `Section("Dictation")` to behavior-only config (hotkey, mode, restore delay)
- Build a shared `SaveDestinations` writer abstraction that all features call
- Refactor existing meeting / voice memo flows onto the new abstraction
- Refactor `DictationCoordinator` to call `SaveDestinations` after the always-on clipboard write
- No migration / no backwards compatibility (app not yet released to users; rip-and-replace `UserDefaults` keys)

**Out of scope:**
- New destinations beyond Notion / Obsidian / Local File (Drive, S3, etc.)
- Configurable subfolder names in Local File (hardcoded for now)
- Per-content opt-in toggles (e.g., "send meetings to Notion but not dictation")
- Removing Phase 18's clipboard write -- ships as-is, always-on for dictation
- DictationOutputMode-related tests (deleted along with the enum)

</domain>

<decisions>
## Implementation Decisions

### Architecture

- **D-01:** Three top-level destinations in Settings -- **Notion**, **Obsidian**, **Local File**. Each is a peer with its own configuration. There is **no Clipboard destination** -- clipboard is an always-on dictation behavior, not a Settings entity.

- **D-02:** Per the architectural rule (memory: `feedback_save_destinations.md`), dictation is content, not a special save feature. Meetings, voice memos, and dictation all flow through the same `SaveDestinations.save(content, metadata)` entry point. Fan-out is **uniform**: a piece of content goes to all enabled destinations.

- **D-03:** Each destination expresses content-type separation in its **native idiom**:
  - **Notion**: single database, `session-type` as a database property on each entry
  - **Obsidian**: single folder, `session-type` as a YAML frontmatter property on each file
  - **Local File**: single root, `session-type` as a hardcoded subfolder (`Meeting/`, `Memo/`, `Dictation/`)

  All three destinations have **one configuration point** (one folder picker / one DB ID); content-type separation is the destination's responsibility, not a per-feature config.

### Local File destination

- **D-04:** `Section("Local File")` has one configuration: a folder picker for the root directory. The app creates three hardcoded subfolders inside that root: `Meeting/`, `Memo/`, `Dictation/` (singular, per user). Subfolder names are hardcoded in this phase; no UI to customize.

- **D-05:** Local File writes preserve existing format conventions per content type:
  - **Meeting / Memo files**: YAML frontmatter (matches today's `TranscriptLogger` output)
  - **Dictation files**: plain markdown, no frontmatter (matches Phase 16 D-01, unchanged for the Local File path)

  The subfolder location identifies session-type; **no `session-type:` frontmatter is added in Local File** (subfolder is sufficient).

- **D-06:** Default `localFileRoot` = `~/Documents/PSTranscribe`. Default `localFileEnabled` = `true` (so meeting / voice memo recording works out of the box without setup). Subfolders are created **lazily on first write** per content type, not eagerly at app launch.

### Obsidian destination

- **D-07:** `Section("Obsidian")` is restructured to **one folder picker** (replacing today's two-folder Meetings + Voice memos shape). All content types (`Meeting` / `Memo` / `Dictation`) write to this single folder.

- **D-08:** Each Obsidian file gets a YAML frontmatter property `session-type: meeting | memo | dictation` for tagging. This is the Obsidian-native equivalent of Notion's database property -- searchable via DataView and Obsidian's properties panel.

- **D-09:** Obsidian vault detection (existing v1.0 behavior -- green / orange / gray status dot, Obsidian deep-link generation in the library) carries forward, applied to the single folder. If the configured folder is inside a vault, deep-links are generated for saved files.

- **D-10:** Today's `vaultMeetingsPath` and `vaultVoicePath` `UserDefaults` keys are **deleted**. Replaced with a single `obsidianFolderPath` key. Default `obsidianEnabled` = `false` (Obsidian is opt-in -- not all users have a vault).

- **D-11:** Dictation files going to Obsidian **gain YAML frontmatter** (since `session-type:` is the tagging mechanism). `DictationLogger`'s plain-markdown output applies to the **Local File destination only**; the Obsidian writer for dictation includes frontmatter. Phase 16 D-01 (plain markdown for dictation) is preserved for the Local File path.

### Notion destination

- **D-12:** Notion fan-out is uniform -- when Notion is enabled (`notionAutoSendEnabled` = true), all content types (meeting / memo / dictation) auto-send to the Notion database. **No per-content carve-outs.** Empty / default values populate properties dictation lacks (no Source App, no Speakers).

- **D-13:** Each Notion entry gets a `session-type` property. Exact Notion property name and shape is a planning / research question -- could be a new Select property `"Session Type"` with values `Meeting / Memo / Dictation`, an existing Tags multi-select, or another mechanism. Confirm during planning by inspecting the user's current Notion database schema.

### Dictation behavior (refactored)

- **D-14:** `Section("Dictation")` is reduced to **behavior-only config**:
  - Hotkey recorder
  - Hotkey behavior (toggle / press-and-hold)
  - Clipboard restore delay

  No output mode picker, no folder picker -- those move to destinations.

- **D-15:** Clipboard write on dictation stop (DICT-05) is **unconditional and always-on**. It is the immediate-paste UX, not a destination. `DictationCoordinator.endDictation()` flow:
  1. Always write final transcript to clipboard with privacy markers (DICT-09)
  2. Schedule clipboard restore (DICT-06)
  3. Independently call `SaveDestinations.save(content, metadata)` to persist to whatever destinations are enabled

- **D-16:** Removal scope:
  - **DELETE**: `AppSettings.dictationOutputMode` + `AppSettings.dictationFolderPath`
  - **DELETE**: `DictationOutputMode` enum from `Models.swift` (was Phase 16 D-09 -- supersede)
  - **DELETE**: dictation output-mode picker + dictation folder picker UI in `SettingsView.dictationSectionContent`
  - **SIMPLIFY**: `DictationCoordinator.beginDictation` / `endDictation` mode-branching (remove `mode == .plainFolder || .both` checks; `SaveDestinations` handles all content routing)

### Migration

- **D-17:** **No migration logic.** App has not been released to users; `UserDefaults` keys can be deleted clean and replaced with new keys. No legacy code paths, no first-launch detection, no read-once-and-translate. Old keys (`vaultMeetingsPath`, `vaultVoicePath`, `dictationFolderPath`, `dictationOutputMode`) are removed entirely from `AppSettings`.

### SaveDestinations writer abstraction

- **D-18:** A new `SaveDestinations` actor or `@MainActor` class is the **single fan-out point**. Exact shape is Claude's discretion at planning time -- candidate shapes:
  - Static methods that read `AppSettings` and dispatch to `NotionService` / `ObsidianWriter` / `LocalFileWriter`
  - An actor holding references to per-destination writer protocols, iterating over enabled destinations

  Each destination has a writer accepting `(content: TranscriptContent, sessionType: SessionType)` and writes in its native format / medium. Per-destination failure is non-fatal: library entry is still created (with inline transcript fallback if zero destinations succeeded).

### Empty-state policy

- **D-19:** **Dictation when zero destinations are enabled**: clipboard write still fires (always-on); library entry stores inline transcript; no file written; user pastes immediately. Clean degenerate path.

- **D-20:** **Meeting / Voice memo when zero destinations are enabled**: **block at session-start** with a clear error ("No save destination configured. Enable Local File, Obsidian, or Notion in Settings."). Long-form recordings don't fit clipboard; persistence is required. Mirrors today's "no vault folder configured" guard.

### Claude's Discretion

- Exact Notion property name and shape for the session-type tag (likely a Select property `"Session Type"`, but confirm against user's existing DB schema during planning).
- New `AppSettings` key names: `obsidianFolderPath`, `obsidianEnabled`, `localFileEnabled`, `localFileRoot`. Pick names consistent with existing conventions (camelCase, descriptive).
- `SaveDestinations` writer abstraction shape -- actor vs static, protocol-per-destination vs concrete writers.
- How `DictationCoordinator`'s existing `inlineTranscript` (Phase 18 D-12) maps to the new flow: when zero destinations succeeded, library entry stores inline transcript; when at least one succeeded, library row points at a destination-provided URL/path.
- Whether the Obsidian writer reuses `TranscriptLogger`'s frontmatter logic or is a new `ObsidianWriter` from scratch.
- Whether `LocalFileWriter` and `ObsidianWriter` are siblings, or share a `MarkdownWriter` protocol.
- Empty-state UX details for `Section("Local File")` and `Section("Obsidian")` (folder not picked, folder doesn't exist on disk).
- How vault detection is presented in `Section("Obsidian")` (status dot color thresholds, vault-name display).
- File-naming conventions for the Obsidian Dictation case: today dictation files use `yyyy-MM-dd HH-mm-ss-SSS Dictation.md` (`DictationLogger`); meeting files use a different scheme. The Obsidian writer needs a scheme that doesn't collide with meeting / memo files in the same folder -- likely keep type prefix in filename (e.g., `2026-04-29 14-32 Dictation.md`).

</decisions>

<specifics>
## Specific Ideas

- **Hardcoded subfolder names**: `Meeting/`, `Memo/`, `Dictation/` (singular). User chose these names explicitly. Hardcoded in this phase; later configurability is a future-feature.
- **Notion property name**: likely a Notion Select property named `"Session Type"` with values `Meeting | Memo | Dictation`. Exact mechanism (new property, existing Tags property reuse, title prefix) is a planning / research question -- **confirm what's in the user's existing Notion DB schema before locking**.
- **Obsidian frontmatter property key**: `session-type` (kebab-case), values `meeting | memo | dictation` (lowercase). Aligns with common DataView usage.
- **`SaveDestinations.save()` return semantics**: returns a per-destination result -- at minimum, the URL / path of any successfully-written file (so library entries can point at it) and a summary of which destinations succeeded / failed. Failures are non-fatal: library entry is still created, with inline transcript when zero destinations succeeded.
- **Library entry source-of-truth path**: today (Phase 18 D-12) the row points at the plain-folder file when one was written, falls back to inline transcript otherwise. After 18.1: row prefers **Local File path > Obsidian path > Notion URL > inline transcript**. Tie-break order is Claude's discretion at planning.
- **Empty-state for Dictation when zero destinations enabled**: clipboard write still happens (always-on). Library entry stores inline transcript. User pastes immediately; record stays in library; no file written. Clean fallback (D-19).
- **Empty-state for Meeting / Voice memo when zero destinations enabled**: block at session-start with a clear error (D-20). Long-form recordings don't fit clipboard.
- **Lazy subfolder creation**: Local File `Meeting/`, `Memo/`, `Dictation/` are created on first write per type, not at app launch. If `localFileRoot` doesn't exist on disk at write-time, create it (with parents) before writing.
- **Vault detection in `Section("Obsidian")`**: walks up from the configured folder looking for an `.obsidian/` directory (existing `obsidianVaultForPath` logic). Status dot: green if vault detected, orange if folder set but not in a vault, gray if nothing configured.
- **Filename collision in Obsidian (single folder, three content types)**: filenames must encode content-type to avoid collisions. Suggested scheme: `YYYY-MM-DD HH-mm-ss-SSS [Meeting|Memo|Dictation] <auto-name>.md`. Confirm during planning.

</specifics>
